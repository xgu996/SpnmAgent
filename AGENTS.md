# AGENTS.md — rules for coding agents working in this repository

The full design is in `docs/GeoStructure-Agent-Blueprint.html` (v0.3). The original task brief
is `docs/GeoStructure-Agent-CLI-Brief.md`. Where they disagree, the blueprint wins.

## Rule 0: code is delivered as lessons, not written into the source tree

This rule overrides any other instruction to "implement" something.

- Every piece of project code (anything under `src/`, `tests/`, `backends/`, plus config
  files such as `pyproject.toml`) is written first into a lesson page:
  `docs/lessons/<phase>-<nn>-<topic>.html`.
- Each lesson page contains:
  - the goal of the step,
  - every file in full, with its exact path and a copy button,
  - an explanation of each file,
  - the commands to run and the expected output,
  - the points the user must check on the mathematics,
  - an acceptance checklist.
- The user then types or pastes the code into the repository themselves. Coding agents must
  **not** create or edit files under `src/`, `tests/` or `backends/`, except when the user
  explicitly asks for it in that turn.
- Agents may freely create and edit `docs/` (including lesson pages) and the root meta files
  (`AGENTS.md`, `CLAUDE.md`, `README.md`, `.gitignore`).
- When a lesson's code was not run (for example because dependencies are missing), the page
  says so plainly ("not run"). Once the user has entered the code, the agent runs the tests
  and reports the real output.
- `docs/lessons/index.html` lists every lesson in order.

Lesson pages are generated by `docs/_build/build_lessons.py`, and the code they embed lives in
`docs/_build/lesson_src/<lesson>/`. Edit those sources, syntax-check them, and rebuild. Never
hand-edit the generated HTML.

## Rule 1: the judge cannot be tampered with

- Never weaken or edit a contract checker, a test, or a tolerance to make a failing result pass.
  When a contract fails, report the failure.
- Any change to contract checkers (`verify`, the contract kits), to tests, or to tolerances must
  be proposed separately and approved by the user.
- Every number in a report must come from program output (`contracts.json`, experiment files),
  never from model-written text.

## Rule 2: MCP

- Target the MCP specification of 2026-07-28: stateless, one server per module, and cross-call
  state passed as explicit handles (`run_id`, `package_id@hash`).
- Do not use the deprecated features Roots, Sampling and Logging.
- Generate tool input and output schemas from Pydantic models, return `structuredContent`, and
  set tool annotations.
- Use the stdio transport locally. Only allowlisted, version-pinned, read-only third-party MCP
  servers may be attached.

## Rule 3: write the article while building

- Every lesson page has an "文章素材" box.
- After each lesson or experiment, append an entry to `docs/article/notes.md` covering: what was
  done, the output files it produced, any decisions, and which article section it feeds.
- The article plan lives in `docs/article/article-plan.html` and is updated as the project
  progresses.

## Repository layout

- Root: only files that tools expect at the root (`AGENTS.md`, `CLAUDE.md`, `README.md`,
  `pyproject.toml`, `.gitignore`).
- `docs/`: design documents, the brief, the blueprint, the lessons (`docs/lessons/`) and their
  build sources (`docs/_build/`), plus the article plan and research log (`docs/article/`).
- `src/geostructure/`, `tests/`: code, entered by the user from the lessons.
- These are local only. They are listed in `.gitignore` and must never be committed or uploaded:
  - all `*.html` files (blueprint, lessons, article plan);
  - `docs/article/` (LaTeX paper, plan, research log), which is versioned by its own local git
    repository with no remote;
  - `docs/_build/lesson_src/` (lesson answer code).
## Rule 4: LaTeX stays plain

- The whole paper is a single file, `docs/article/paper.tex`. Do not create subdirectories or
  split it into `\input` files.
- Use the plain `\documentclass{article}`. Packages are limited to `amsmath`, `amssymb` and
  `graphicx`. Do not use journal style files, decorative or "fancy" packages, colors, custom
  boxes or todo packages.
- Write tables inline with `tabular` and references inline with `thebibliography`. When figure
  files exist, they sit next to `paper.tex`.
- Notes that are not yet text go in `%` comments, not in macros.
- Build with `pdflatex paper.tex`, run twice.
- A journal template is applied only at submission time, and only if the user asks.

## What this project is

A library-level system for energy-preserving numerical methods for complex fluids and
Hamiltonian systems, using GSGE (generalized skew-gradient embedding, Gu & Wang) as the
intermediate language. A deterministic Python kernel does the mathematics and checks the
contracts. A thin LLM agent layer calls that kernel through tools.

## Three principles

1. **The LLM proposes and the deterministic kernel decides.** Every structural conclusion
   comes from a contract checker in the kernel, never from model text.
2. **There are five modules in one pipeline:** Structure → Space → Time → Solve → Experiment.
   Modules exchange only Packages that have passed their audits.
3. **Every claim states its assumptions and its evidence level** (see the Status enum below).

## Scope

- Energy preservation comes first, built out vertically. That means discrete energy
  conservation for conservative systems, the discrete energy law or energy stability for
  dissipative systems, and linear invariants such as mass. Work goes ODE → 1D PDE → NS / CHNS
  → backends → complex fluids.
- Symplectic, Poisson, multisymplectic, positivity and entropy-stable structure are horizontal
  extensions planned for P10+. Do not implement them before then.
- Do not implement anything past the current phase (see `docs/progress.md` once it exists).
  Do not create empty directories or unused classes "for later".

## Layering rule

Dependencies point downward only. These packages must never import an LLM SDK:
`core`, `gsge`, `structure`, `space`, `time`, `solve`, `experiments`, `spec`, `cli`.
The project must run its deterministic experiments with no API key.

## Role boundaries (borrowed from GradAgent)

- The Structure stage does not choose schemes or write solver code.
- The Scheme stage (space + time) does not change a released Structure Package.
- The Program stage (solve + experiment) does not change a released scheme or its
  computational order. Its conclusions must come from runs of the current program version.

## Evidence levels

`proved_under_assumptions` · `symbolically_checked` · `numerically_supported` · `failed` ·
`unknown` · `not_run` · `not_applicable`.

- `proved_under_assumptions` requires a human-auditable derivation or an applicable theorem,
  and every assumption must have been checked.
- A SymPy simplification or a floating-point test alone never earns `proved_under_assumptions`.

## Mathematical rules

- Keep mathematical objects, schemes, checkers, plotting and reporting separate. Solvers must
  not plot or write reports.
- Every claim of "energy conserving", "energy dissipative", "unconditionally stable" or
  "mass conserving" must state:
  - the model conditions and the boundary conditions,
  - the discrete definitions,
  - the solver tolerance,
  - its evidence level.
- An energy plot alone must not be used to infer a structural property, and good long-time
  behaviour must not be called exact conservation.
- Track external power, boundary energy flux, nonlinear-solver residuals and quadrature error
  explicitly. Never drop them silently.
- Report the ZEC defect δ_h = ⟨X_h, J_h⟩ of every spatial discretization. Do not claim a
  discrete energy law unless δ_h is zero or the projection gauge is in use.
- A failed nonlinear solve must fail the run loudly. Never skip a time step or fabricate data.
- When a mathematical property is conditional or uncertain, mark it `unknown`. Do not invent
  assumptions.

## Engineering rules

- Python ≥ 3.11 (pinned to 3.12 via uv), src layout, package name `geostructure`.
- Work in small steps. Each step adds tests, runs `pytest -q`, and reports real output. If
  something could not be run, say `not run`; never claim a test passed without running it.
- Cite the source equation in docstrings for every GSGE/SGE formula (e.g. "GSGE Prop 3.4").
- Do not fabricate citations, theorem numbers, proofs, experiment results or logs.
- Read secrets only from environment variables, and never commit them.
- Do not modify existing research code outside this repository.

## Commands

The environment is managed with uv. Python is pinned in `.python-version` (3.12) and
dependencies in `uv.lock`. Always commit `uv.lock`.

```bash
uv sync            # create or update .venv from pyproject.toml + uv.lock
uv run pytest -q   # run tests inside the project environment
uv add <pkg>       # add a runtime dependency (only when a lesson introduces it)
uv add --dev <pkg> # add a development-only dependency
```

- Do not use bare `pip install` for project dependencies.
- Optional groups (agent, local models, PETSc, knowledge graph) are added in the phase that needs
  them, never in advance.
- If PETSc / petsc4py cannot be built from PyPI in P4, solve that single package with conda-forge
  or Docker and document it in the lesson.

## Reporting at the end of each step

List the files created or changed, the commands run, the tests that passed or failed, and which
mathematical statements were proved, symbolically checked, only numerically supported, or not
yet verified. Then name the next smallest task.
